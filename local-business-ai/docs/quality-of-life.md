# Quality of Life Standards

## Purpose

This document defines the platform-wide quality of life standards for the Local Business AI platform.

These are non-negotiable operational rules that apply to every audit module, every workflow, and every AI model configured to run on this platform. They exist to protect report quality, operator trust, and client confidence.

---

## Standard 1 — Automatic Report Saving

**Every generated report must be saved automatically without requiring operator intervention.**

- Reports are never held in memory only. A completed report is always written to disk before the workflow ends.
- The save must complete before the workflow signals completion.
- If a save fails, the workflow must surface a clear error and halt — it must not silently continue or report success.
- Reports are saved to `clients/{client}/reports/` following the platform naming convention defined in `/templates`.

**Rationale:** An unsaved report is a lost deliverable. Operators should never have to manually save or export — the platform handles it.

---

## Standard 2 — Save Location Transparency

**Every generated report must display its save location to the operator upon completion.**

The confirmation message must include:
- The full file path where the report was saved
- The filename (including version identifier and date)
- The file format (PDF, Markdown, HTML)
- The file size

**Example output:**

```
Report saved successfully.
Location : clients/demo-business/reports/gbp-audit-2025-03-15-v1.pdf
Format   : PDF
Size     : 284 KB
```

**Rationale:** Operators need to know exactly where to find the output without searching the filesystem.

---

## Standard 3 — Graceful Failure

**The platform must never crash, freeze, or silently skip data when a source is unavailable.**

When any data source fails or returns incomplete data, the platform follows this protocol:

### If Google Business Profile data is unavailable:
- Continue immediately with website analysis
- Continue with review analysis if review data is available
- Mark the GBP section clearly in the report as: **"Data Unavailable — GBP data could not be retrieved at time of audit"**
- Document the failure reason in the audit log

### Universal rules for all data sources:
- **Never fabricate information.** A missing field is always marked as missing — never estimated, assumed, or invented.
- **Never silently skip a module.** If a module cannot run, it must appear in the report with a clear unavailability notice.
- **Never halt the entire workflow** because one data source failed. Other modules continue unless they have a hard dependency on the failed data.
- **Always log the failure** to `logs/` with the timestamp, module name, source, and error detail.

### Marking missing data:
Missing or unavailable data must be displayed consistently across all reports using this format:

```
[Data Unavailable — {reason}]
```

Examples:
```
[Data Unavailable — GBP API returned no results]
[Data Unavailable — Website unreachable at time of audit]
[Data Unavailable — No reviews found on this platform]
```

**Rationale:** A partial report with clear gaps is more trustworthy than a complete report with fabricated data.

## Standard 4 — Professional Report Tone

**Audit reports are professional business documents. They must never be rewritten to sound casual.**

All report content — whether generated by the `report-writer` skill or any configured AI model — must adhere to the following:

- Use formal, professional business English at all times
- Use precise, specific language — avoid vague filler phrases
- Use active voice where possible
- Do not use colloquialisms, slang, contractions, or casual phrasing
- Do not use emojis, exclamation marks for enthusiasm, or conversational asides
- Do not soften findings to make them more comfortable — accuracy takes precedence over tone

The `report-writer` skill must apply the rules in `/shared/STYLE_GUIDE.md` without exception.

**Rationale:** Clients receive audit reports as formal business deliverables. Casual language undermines the credibility of the findings.

## Standard 5 — Humanization Scope

**Humanized AI writing is permitted only in specific output types. It is explicitly prohibited inside audit reports.**

### Humanization is permitted for:
- Cold emails
- Follow-up emails
- Sales proposals
- Outreach messages

### Humanization is explicitly prohibited in:
- Google Business Profile audit reports
- Google Reviews analysis reports
- Website audit reports
- Local SEO audit reports
- Citation audit reports
- Competitor analysis reports
- Any section of a combined audit report
- Executive summaries within audit reports
- Priority action plans within audit reports

**Definition of humanization in this context:**
Humanization refers to the deliberate stylistic adjustment of AI-generated text to make it sound more conversational, warm, informal, or less detectable as AI-generated output. This style is appropriate for outreach content where relationship tone matters, but it is incompatible with the neutrality and precision required in audit documentation.

**Rationale:** Audit reports derive their authority from objectivity and precision. Humanized language introduces a tone that is inconsistent with professional analysis documents and undermines operator credibility with clients.

## Standard 6 — Status Messaging

**Every module and skill must emit clear, human-readable status messages throughout execution.**

Status messages keep operators informed during long-running audit workflows and provide a real-time activity log that can be surfaced in the platform UI or written to `logs/`.

### Required status message points:

Every workflow and skill must emit a status message at minimum at these points:
- **When starting** a task
- **When completing** a task successfully
- **When an error or warning** occurs

### Standard status message format:

```
[STATUS] Module/Skill Name — Message
```

Where STATUS is one of:
- `INFO` — normal progress update
- `WARN` — non-blocking issue detected, continuing
- `ERROR` — blocking failure, operator action required
- `DONE` — task completed successfully

### Platform-standard status messages by module:

| Stage | Status Message |
|---|---|
| Starting data collection | `Collecting Business Data...` |
| Starting review processing | `Analyzing Reviews...` |
| Starting website analysis | `Analyzing Website...` |
| Starting local SEO analysis | `Analyzing Local SEO Signals...` |
| Starting citation analysis | `Analyzing Citations...` |
| Starting competitor analysis | `Analyzing Competitors...` |
| Starting scoring | `Scoring Audit Findings...` |
| Starting recommendation generation | `Generating Recommendations...` |
| Starting report assembly | `Generating Report...` |
| Starting PDF export | `Exporting PDF...` |
| Workflow complete | `Completed.` |
| Data source unavailable | `[WARN] GBP data unavailable — continuing with available modules.` |
| Save confirmed | `Report saved to: {filepath}` |

### Rules:
- Status messages must be written in plain language — no technical jargon visible to operators
- Messages must be emitted in real time, not batched at the end
- Errors must include enough detail for the operator to understand what failed and why
- The final message of any successful workflow is always: `Completed.`

**Rationale:** Silent execution erodes operator trust. Operators need to know what the platform is doing at all times, especially during long audit runs.
